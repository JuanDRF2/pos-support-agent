### 2026-09-28 — Task 7: retrieve and answer logic (refusal decided in code)
- **What:** `src/rag/retrieve.ts` (embeds the trimmed question on its own, returns top-k with scores) and `src/agent/answer.ts`. `answer()` neutralises any run of three or more `<`/`>` characters in the question and in chunk text (so the prompt's delimiters cannot be forged), refuses without calling the model when the top score is below the threshold (a score exactly at the threshold goes through), builds a prompt with the context and the question in separate delimited sections, and refuses when the reply is empty or contains `NOT_IN_DOCS` anywhere. The `Source:` value comes from the top chunk's metadata, never from model text; replies are capped at 1,500 characters at a word boundary. Errors from the generator are not swallowed.
- **Interpretation to confirm:** the plan said "strict `NOT_IN_DOCS` match". I made it strict about the token (exact spelling, case-sensitive) but not about position: a reply that contains it inside a longer sentence is also refused. Reason: showing a possibly-wrong answer is worse than an extra refusal, and a small model often adds words around the sentinel.
- **Measured retrieval (read-only look, nothing calibrated yet):** top-1 finds the expected article for all 15 answerable golden questions. Top-1 scores: answerable 0.42-0.77, traps 0.21-0.56 (`g16` gift card 0.56, `g18` cancel subscription 0.54, injection `g23` 0.51). No threshold separates the two groups, as the architect predicted, so the far traps (0.21-0.39) rely on the threshold and the near traps on the model's `NOT_IN_DOCS`. Task 11 decides the final threshold from end-to-end refusal results.
- **Why:** AC1 (retrieval), AC2 and AC3 (refusal decided in code), AC10 groundwork (source from metadata) and the prompt-injection mitigations from the security audit.
- **Acceptance:** `npm run test:unit` 44 pass, 0 skipped. Live tests confirm the partial-refund question lands on "Issuing a Partial Refund" and every answerable golden question finds its article first.
- **Touched:** `src/config.ts` (`MAX_ANSWER_CHARS`), `src/rag/retrieve.ts`, `src/agent/answer.ts` and their tests.

### 2026-09-28 — Task 9: local server and chat page (9.1 done; browser check in 9.2 pending)
- **What:** `src/server/server.ts` (Node `http`, bound to `127.0.0.1`), `src/server/index.html` (the screen from the proposal), `src/index.ts` (startup) and a `PORT` setting (default 3000, range-checked). Rules, each with its own test: `Host` must be `127.0.0.1:PORT` or `localhost:PORT` (403; a missing Host on HTTP/1.0 is also 403, on HTTP/1.1 Node itself answers 400); `POST /api/chat` needs `Content-Type: application/json` (415) and, when an `Origin` header exists, it must be the server's own (403); no CORS headers on any response; fixed routes only (`/`, `/index.html`, `/api/chat`; everything else 404, wrong methods 405, no file path is built from the URL); body over 10 KB gets 413 whether declared or streamed, and the socket is closed; body must be a JSON object with exactly one string `question`, trimmed, non-empty, at most 500 characters (400); one generation at a time (429 with `Retry-After`); header and request timeouts; `maxHeaderSize` 8 KB. Ollama, model and index problems become a plain 503 with their own message; anything else is a generic 500 with no internals. Logs hold only `kind`, error class name and milliseconds. The page is sent with a Content-Security-Policy that pins the single inline script and style by sha256 (no `unsafe-inline`), plus `nosniff`, `no-store` and `no-referrer`. The page builds everything with `textContent` and text nodes (bold `**...**` becomes `<strong>` elements built in code), has no inline handlers or styles and no external resources. Startup fails with a plain message if the model files, the index or the settings are wrong, and only warns if Ollama is not up yet.
- **Finding (server bug the tests caught):** Node checks connection timeouts only every `connectionsCheckingInterval`, 30 seconds by default, so the 15 s `requestTimeout` would have let a slow-dripped request live for up to about 45 s. Now set to 1 s; the slow-drip test proves the cut.

AC2 returned the refusal in 3.9 s. Foreign Host 403, foreign Origin 403, `text/plain` 415, 20 KB body 413. The server log had no trace of the marker text put in the question. Note: the earlier `try.ts` run of the same AC1 question left out the 30-day sentence, so answer completeness varies with small changes to the question text; the eval will show how often.

### 2026-09-28 — Task 10: deterministic scorers, scorecard and the first real numbers
- **What:** `src/evals/score.ts` (the three scorers), `src/evals/report.ts` (evaluation, scorecard text, exit code as pure functions), `src/evals/run.ts` (CLI), `src/evals/passmarks.ts` (all `null`), a small `onRetrieved` hook in the pipeline so the eval scores an answer against exactly the chunks the model saw, and the scripts `eval:fast`, `test` (unit tests, then the full eval) and `verify` (now also runs `eval:fast`). Retrieval: the expected article is among the top 3 chunks. Faithfulness (only for answers actually given): cites the expected article, contains the key phrases, and every amount, time period, number and bold or quoted option in the answer also appears in the retrieved text or in the question. Correct refusal: every trap and injection refused, every answerable question answered. The scorecard reports all questions and held-out only. A category that could not run shows `SKIPPED` with no number, the refusal category then shows only a clearly labelled threshold-only figure, and any category that is not fully scored makes the full run exit 1. Missing model files or index stop the run with a plain message.
- **Two scorer weaknesses found and fixed by running it (both disclosed):** (1) checking bare numbers let an invented "$5.00" pass, because "5" appears in "5-7 business days"; numbers are now compared by type (amount, time period with its unit, plain number), with tests. (2) The model repeating the merchant's own words ("six weeks ago") was flagged as an invented number; what the merchant wrote in the question now counts as known. Neither change touches the golden set or the pass marks. Spec and loop-contract wording for check 3 was updated to match.
- **First real results (`npm test`, `llama3.2:3b`, threshold 0.35, top-k 3, 23 questions, 6 held out; temperature 0, seed 7):**

  | Category | All | Held-out only |
  |---|---|---|
  | Retrieval | 15/15 (100%) | 4/4 (100%) |
  | Faithfulness (15 answers) | 14/15 (93%) | 3/4 (75%) |
  | Correct refusal | 23/23 (100%) | 6/6 (100%) |

  The only failure is held-out `g14` ("refund an order from six weeks ago"): the answer is right about the 30-day rule but leaves out "general support" (the same incompleteness noted when the prompt was tuned). Two full runs gave the same pass/fail set. Time per question: average 8.7 s and slowest 21.9 s on the first run, average 6.7 s and slowest 15.2 s on the second (model already loaded), well under the 60 s limit. The near-miss traps ("refund a gift card", "cancel a subscription") and both injection cases were refused, even though the threshold alone refuses only 2 of the 8 questions that must be refused: the other 6 were refused by the model's `NOT_IN_DOCS`.
- **Read these numbers with care:** 23 questions means each one is about 4 points and each held-out one 25 points; the golden set was written from the same three short articles the model reads, and the prompt was tuned on the non-held-out questions, so these are demonstration figures, not a general accuracy claim. ### 2026-09-28 — Task 11 decision: threshold 0.30, pass marks 90% / 85% / 95%, retrieval scored by section
- **Decision (approved by Juan):**
  - **Refusal threshold 0.30** (was a provisional 0.35). On the golden set every value from 0 to 0.40 gave the same end-to-end result, and 0.45 starts refusing a legitimate paraphrase (`g09`, top score 0.42). 0.30 still refuses the same two clearly off-topic questions before they reach the model (`g22` at 0.21 and `g20` at 0.29) and keeps a 0.12 margin from the lowest answerable score, against 0.07 at 0.35 and 0.02 at 0.40. The data cannot tell values inside the plateau apart, so this is a judgement about margin, not a measured optimum. That the model refuses every trap by itself is an observation on these 23 questions, not a guarantee, so the threshold does not lean on it.
  - **Pass marks, one question of slack each:** retrieval 90% (at least 14 of 15), faithfulness 85% (at least 13 of 15, which allows the known `g14` miss plus one more), correct refusal 95% (at least 22 of 23). They are regression alarms, not goals. Held-out results are reported but do not gate (6 questions, 25 points each).
  - **Retrieval is now scored by section:** every answerable golden question lists the heading(s) of the section that answers it (`sourceHeadings`, validated against the real `##` headings), and a hit needs the article and one of those headings in the top 3. Choices Juan can review: `g10` (how long until a card refund shows) accepts both "Issuing a Full Refund" and "Issuing a Partial Refund" because both articles state the 5-7 day timing; `g14` accepts only "Issuing a Full Refund", where the 30-day rule and "general support" live. The scorecard also says how often the expected section is the very first chunk.
- **Results with these settings (`npm test`, `llama3.2:3b`, 23 questions):** retrieval 15/15 (100%), held-out 4/4; the expected section is the first chunk in 14 of 15 (`g09` has it second: "Issuing a Full Refund" 0.42 against the correct "Issuing a Partial Refund" 0.40, almost a tie). Faithfulness 14/15 (93%), held-out 3/4 (75%), with the same single miss (`g14`, missing "general support"). Correct refusal 23/23 (100%), held-out 6/6. Result OK; average 9.8 s per question, slowest 19.5 s.
- **Overfitting risk, stated for the record:** (1) Juan wrote both the articles and the questions, and the model reads those same three short texts, so a perfect score says little about other wording. (2) The index has only 10 chunks and the top 3 cover 30% of it, and there are only 3 articles, which is why the metric moved to sections. (3) The 6 held-out questions were not used to choose the threshold, but they have been seen several times (prompt confirmation, full runs, this grid) and are only weakly independent. (4) The 0.42 lower bound comes from a single question, an observed edge and not a distribution. (5) There is one phrasing per intent, so a rewording can change a result without the eval noticing. (6) With 15 and 23 questions a percentage moves in steps of 4 to 7 points. (7) Reproducibility was checked only on this machine with a fixed seed: two runs were identical.
